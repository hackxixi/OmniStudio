# 产品方向：能力基座 + 以 Agent 为入口的简洁模式

> 建立于 2026-09-24，汇总这一轮产品讨论的结论。
> 与其他文档的分工：[architecture.md](./architecture.md) 讲「东西在哪」，
> [ROADMAP.md](../ROADMAP.md) 讲「已排期的里程碑」，本文讲「接下来往哪走、为什么」。
> 本文里标 **【已定】** 的是已拍板的决定，标 **【待验证】** 的要等实验数据再定。

## 1. 出发点

OmniStudio 要做的是**集成各类 AI 模型能力的综合基座**：

- Agent 能**看到并调用**各种多模态模型的能力和它们的产物，组合成工作流，完成单个模型做不到的任务；
- 用户不再自己调模型：选哪个模型、用什么量化、给多少上下文、本地还是云端，由基座决定；
- 先弄清**本机能独立跑什么**，剩下的用云端 API 补，默认走 OmniLabs（内置厂商 `omnilabs`，
  `shared/cloud-providers.ts`）；
- 用户只选一个原则：**尽量本地**还是**能力优先**，基座在这个原则下压低使用成本。

## 2. 现状盘点（2026-09-24）

### 2.1 Agent 能调用哪些能力

| 能力 | 界面 | Agent 工具 |
|---|---|---|
| 生图 / 改图 | ✅ | ✅ `generate_image`（可带 `reference`） |
| 视频（含图生视频） | ✅ | ✅ `generate_video`（`first_frame`） |
| 语音合成 | ✅ | ✅ `generate_speech` |
| 产物检索与复用 | ✅ | ✅ `media_search` / `media_export`（产物用 ref 在工具间传） |
| 知识库 / 记忆 / 笔记 | ✅ | ✅ |
| 类型化判断（JEV） | ✅ | ✅ `jev_evaluate` |
| 看图 | ✅ | 🟡 `view_image`，只在主模型本身支持视觉时注册，不会转交视觉模型 |
| 语音转写（ASR） | ✅ | ❌ |
| OCR / 文档解析 | ✅ | ❌ |
| 音乐生成 | ✅ | ❌ |
| 抠图 | ✅ | ❌ |
| 视频 / 音频理解 | ❌ | ❌ |

**结论：生成侧基本打通，感知侧（听、读、看）没有接给 Agent。** 跨模态任务大多从感知开始
（录音 → 纪要、扫描件 → 翻译），所以这是组合能力的主要缺口。

### 2.2 结构问题：界面和 Agent 是两套平行实现

每接一种能力，都要写一次界面、再写一次 Agent 工具。已经造成的后果：

1. 两边能力不对齐（上表的 ❌）；
2. Agent 不知道哪些能力**此刻可用**（权重下没下完、Key 填没填），而小应用那边已经有就绪检查
   （`getMiniAppCapabilities`）；
3. 网关只对外开放了对话和 SystemOne，外部 Agent 用不到多模态能力。

### 2.3 「本机能做什么」这条链路

| 层 | 要回答的问题 | 现有代码 | 缺口 |
|---|---|---|---|
| 环境画像 | 这台机器有什么 | ✅ `bun/hardware.ts`：芯片、显存 / 统一内存、推理预算、实时占用 | 磁盘余量、内存带宽（决定生成速度） |
| 可部署性 | 装得下、跑得动吗 | 🟡 `shared/hardware.ts`：`estimateModelMemory` / `fitModelsForMachine` | 只在首次启动引导里用；只看文本模型、只看「装得下」，没算速度 |
| 能力评估 | 能胜任哪些工作 | 🟡 `bun/eval.ts` 八套评测 | 结果没写回成模型的能力档案；没有「任务需要什么能力」的定义 |
| 路由策略 | 本地还是云端 | 🟡 设置 → 默认模型（按场景选模型） | 缺用户原则、预算、隐私规则、失败后升级 |
| 成本账本 | 花了多少、省了多少 | 🟡 `bun/usage.ts` 记 token | 没有价格，不计钱 |

## 3. 目标形态

### 3.1 两种界面模式 【已定】

- **高级模式**：就是现在的界面，完整保留，面向会调参的用户和开发者。
- **简洁模式**：面向新用户，**以 Agent 为主入口**。用户想用某项模型能力，直觉路径就是
  跟 Agent 说需求，由 Agent 组合各模型能力完成。

两种模式**共用同一套后端和同一份数据**，简洁模式只换呈现方式，不能自带一份业务逻辑
（这条要写进 AGENTS.md，否则两边会各自演进）。

简洁模式首页的设想：

1. **Agent 对话**：占大部分面积；
2. **能力状态条**：例如「对话 L2 本机 · 看图 可用 本机 · 语音 ✓ · 生图 → 云端」，点开看
   每项能做什么、怎么升级；
3. **产物区**：最近生成的图 / 音频 / 文档，可以拖回对话继续用。

首次启动：检测环境 → 推荐「本机套装」（Agent 模型 + ASR + TTS 等一组）→ 一键下载 →
**下载期间先用 OmniLabs 顶上**，第一分钟就能用。

### 3.2 其他入口按使用频率展示 【已定，细节待定】

建议避免实时重排（按钮位置跳动会破坏肌肉记忆）：

- **固定核心**：Agent、产物、设置，位置永远不动；
- **常用区**：每周重排一次，最多 4～6 个；
- 常用区里放的最好是**用户自己的快捷卡**，而不是我们的应用列表：Agent 完成一次任务后可以
  「存成快捷方式」（如「拍照 → 翻译成英文」），下次点一下就跑，不必再对话。

### 3.3 简洁模式下的 Agent 权限

新用户不理解「授权执行命令」。简洁模式默认用专用工作区 + `workspace-write` 沙箱，
不弹技术性授权卡片，危险操作一律拒绝并解释原因。

## 4. 执行能力与能力等级

把抽象的模型参数（参数量、量化、上下文、引擎）概括成两件事：**能做什么**（执行能力）
和**做到什么程度**（能力等级）。

### 4.1 等级按「能完成什么任务」定义 【已定】

**Agent 用四级**，其他能力用三档。Agent 是基础：其他能力都要靠 Agent 串联调用。

| 等级 | Agent 能力 | 验收任务举例 |
|---|---|---|
| L1 | 问答、改写、摘要 | 单轮，不调工具 |
| L2 | 单步调用工具 | 查资料再回答；生一张图；转写一段录音 |
| L3 | 多步组合 | 录音 → 纪要 → 配图；读 PDF 整理成表格 |
| L4 | 长时间自主执行 | 改代码并跑测试；带验证的十步以上任务 |

- 每一级就是**一组固定的验收任务**。某个模型在某个量化、某个引擎下通过该级 X% 以上的任务，
  就算达到该级。等级就是对用户的承诺：「本机 Agent 达到 L2 = 单步任务靠得住，多步任务会
  交给云端」。
- Agent 的验收**用我们自己的 Agent 框架跑**（我们的工具集和系统提示，
  即 `docs/agent-optimization` 的基线用例），不用通用榜单：同一个模型在不同框架下调用
  工具的表现差别很大。
- **其他能力三档**：不可用 / 可用 / 好用，每档附一句代表性的「能做什么」
  （例如看图「可用」= 认得出物体和文字，看不懂复杂图表）。

### 4.2 等级包含速度

32B 在本机每秒只出 3 个 token，跑 Agent 就等于不可用。展示给用户的是**可用等级**，
由三个条件共同决定：

- 质量达标（查能力数据库）；
- 速度过线（例如 Agent 生成 ≥ 15 token/s）——**在用户机器上实测**，部署后跑 30 秒测速，
  并用内存带宽估算值校准；
- 上下文够用。

## 5. 能力数据库 【已定】

「这个模型在这个量化、这个引擎下，跑我们的 Agent 能到几级」这份数据只有我们有，
是护城河。

- **范围**：前期**只测魔搭社区（ModelScope）上的模型**。每类能力精选常用模型系列，
  每个配 3～4 档量化（GGUF Q4_K_M / Q5 / Q8，MLX 4bit / 8bit）。
- **维度**：模型 × 量化 × **引擎**。llama.cpp / MLX / vLLM / SGLang 解析工具调用的方式
  不同，同一模型的 Agent 等级可能差一级，引擎必须是独立维度。
- **设备**：有专门的设备长期跑评测；CUDA 侧可用 ycs2。
- **更新**：**按新模型发布触发**，不按固定周期。
- **分数来源必须标注**，按可信度分三档：公开榜单 < 参考设备实测 < 真实使用中的成败统计。
  没测过的组合用「同系列 + 量化折损曲线」推测，标成「估计」，永远不冒充实测；
  完全没依据的显示「未评估」。
- **分发**：带版本号的 JSON，随应用发布，可从 OmniLabs 远程更新。
- **评测流水线**复用 `bun/eval.ts` 和 agent-opt 的门禁脚本（`docs/agent-optimization/gate.sh`）。
- JEV 自己也要进数据库：**判断能力等级**是一个独立维度（本地 laya-mlx / NanoJev 与
  35B OpenJev 的差距还没测过）。

## 6. 路由与成本

### 6.1 用户原则

| 档位 | 含义 |
|---|---|
| 仅本地 | 完全离线，做不了就直说 |
| 尽量本地 | 本地能胜任就用本地；失败或明显不行时，征得同意后升级到云端 |
| 平衡 | 按「质量 ÷ 成本」挑 |
| 能力优先 | 直接用最强的可用模型 |

附加项：月度 / 单任务预算上限；**隐私标记**（标了敏感的数据永不出本机，优先级高于档位）；
超预算或升级到云端前是否要确认。

### 6.2 OmniLabs 作为默认云端 【已定】

- 需要**注册**，有**免费额度**，简洁模式里**显示余额**；
- 每次交给云端都要**说明原因和花费**（「这张图表本机看不懂，交给云端，约 ¥0.02」），
  依赖默认云服务的产品，信任就靠这一点；
- OmniLabs 不可用时，回退到用户配置的其他厂商。

### 6.3 Agent 怎么用路由

- **统一的能力目录**：每项能力（`image.generate` / `audio.transcribe` / `doc.ocr` …）只
  声明一次：名称、输入输出类型（统一用产物 ref）、可选后端（本地 / 云端）、就绪状态、
  等级、价格。由它派生出 Agent 工具、网关接口，以及系统提示里「你现在能用什么」那一段
  （不可用的也列出来，附开通方法）。新增一种能力 = 目录里加一条 + 一个适配器。
- **开工前报预算**：「预计本地 3 步、云端 1 步，约 ¥0.2」，超阈值先问用户。
- **逐级升级**：先本地执行，再用验证手段（测试、JEV 判断、格式校验）检查，不达标才升级到
  云端重做，并记录原因。
- **成本账本**：云端模型条目加价格，用量记录计钱；本地记 0，但记耗时。可以向用户展示
  「本地替你省了多少」。

## 7. 编排：JEV 负责决策，小模型负责填参数 【待验证】

本地小模型编排能力弱，难点不在「写出一段 JSON」，而在「下一步该做什么、做完了没有」。
后者正是 JEV 的类型化判断擅长的。

| 角色 | 谁做 | 怎么做 |
|---|---|---|
| 选下一步 | JEV `choice` | 选项 = 此刻可用的工具 + 「已完成」 + 「问用户」 + 「交给云端」 |
| 填参数 | 小模型 | 按工具参数定义做**约束解码**（llama.cpp / SGLang / vLLM 都支持按 JSON 结构约束输出），保证参数合法 |
| 判断完成 | JEV `noul` / `score` | 产物 + 原始需求一起判；图片先过视觉，音频先转写 |
| 流程控制 | 代码（状态机） | 步数上限、重试、升级都是确定性的 |

打砖块实验（`app/jev/playground/`）留下的两条经验直接适用：

1. **概率就是「我没把握」的信号**：前两名选项的概率很接近时就是没有信号
   （`isBreakoutCoinFlip` 的思路），此时升级到云端或问用户，而不是硬选一个；
2. **只把此刻可行的选项交给 JEV**：打砖块里去掉「往墙里推」这个选项后，顶墙次数直接归零。
   编排里也一样：前置条件不满足的工具（比如还没有图就不能「改图」）先用代码过滤掉。

需要正视的难点：

- **JEV 只能在给定选项里挑，不能凭空拆解任务。** 多步计划要么来自**计划模板库**
  （快捷卡和成功案例自动沉淀，由 JEV 选模板），要么由**小模型生成 3～5 个候选计划，JEV 打分挑选**。
- **和现有 Agent 内核不兼容**：pi-agent-core 的循环假设「一个模型生成工具调用」。分工模式
  要换成自己的控制器，实现成另一种 Agent 驱动方式；工具、事件流、界面都复用。

### 7.1 开源参考

| 项目 | 相同点 | 可借鉴 |
|---|---|---|
| [HuggingGPT / JARVIS](https://github.com/microsoft/JARVIS) | 一个控制器调度几十个专家模型完成多模态任务：规划 → 选模型 → 执行 → 汇总 | 四阶段流程；但它的控制器是大模型，正是我们要替换的部分 |
| [TinyAgent](https://github.com/SqueezeAILab/TinyAgent) | 1.1B / 7B 小模型在端侧做工具调用 | ToolRAG（先检索相关工具再选，可放在 JEV 选择之前缩小选项）；LLMCompiler（计划组织成有依赖的步骤图） |
| [Octopus v2](https://huggingface.co/NexaAI/Octopus-v2) | 函数名做成特殊 token，选工具变成分类问题 | 和 JEV 从选项里挑一个同一思路 |
| [ToolOrchestra](https://arxiv.org/abs/2511.21689) | 8B 编排模型调度更强的工具与模型 | 奖励同时考虑结果、效率、用户偏好，对应「尽量本地 / 能力优先」 |
| [RouteLLM](https://github.com/lm-sys/routellm) | 强弱模型间路由以省成本 | 用失败 / 升级案例训练路由器 |
| [Agent-as-a-Router](https://arxiv.org/pdf/2606.22902) | 没有标准答案时，把多个验证信号汇总成置信度 | JEV 判断完成时可以和格式校验、测试结果合并 |

用「输出概率的判断模型」当控制器并兼任完成度判定，这种组合没有找到现成实现：
这是差异化，也意味着要先自己验证（见 §9）。

## 8. 失败案例库 【已定】

测试期间把用户执行失败的任务收集成案例库，它覆盖的是我们自己想不到的场景。

- **收什么**：失败的任务；**本地失败、升级到云端后成功**的任务（训练路由最有价值的样本）；
  用户点了「不满意」的任务。每条记录：需求原文、能力链（哪些能力、哪些模型）、在哪一步
  失败、失败类型、JEV 各步的置信度。
- **隐私是底线**：默认只存在本机；上传到 OmniLabs 必须逐条或按开关明确同意；上传前用
  `redactSecrets()` 脱敏；文件内容默认不传，只传结构。
- **怎么用**：
  1. 改写成可复现的合成用例，加入等级验收集（真实任务依赖用户文件，不能直接复现）；
  2. 统计 JEV 置信度与最终成败的关系，校准「多高的置信度才能留在本地」；
  3. 哪类任务失败最多，就先补哪种能力、先测哪个模型。

### 9.1 E1 实验设计

问题：**「JEV + 小模型」在 L2 任务上，能否达到「中等模型直接跑 Agent」的水平？**

- 环境：ycs2（不碰生产的 hq-e）。JEV = 35B OpenJev（`/jev/openjev`）；小模型 = 魔搭
  `Qwen/Qwen3.5-4B`；中等模型 = 同一台 SGLang 上的 Qwen3.6-35B-A3B。
- 任务：20～30 个 L2 单步任务，工具全部用确定性桩（返回固定结果），保证可复现。
- 三组：
  - **A** 小模型独立跑 Agent；
  - **B** JEV 选步骤、判完成，小模型按 JSON 结构约束填参数；
  - **C** 35B 独立跑 Agent（参照）。
- 指标：完成率、工具选对率、参数正确率、步数、延迟，以及「没把握时升级」的触发率是否合理
  （升级的任务里有多少是 A 组确实会做错的）。
- 判定：B 明显好于 A、接近 C → 方案成立，进入 B3。

实验脚本与结果放在 `docs/experiments/e1-jev-orchestration/`。

**第一轮结果（2026-09-24）**：任务对 4B 太简单（4B 原生 92%、JEV + 4B 88%、35B 原生 92%），
JEV 调度没带来准确率提升、耗时 +45%；但 JEV 选步骤 52 次全对，且**JEV 当验收员**在 0.85 阈值下
零误报拦下一半错误（含 35B 谎称已设提醒）。剩余错误集中在参数里的推理（相对日期、尺寸枚举）。
第二轮换更小模型、更多工具、更长链路再测调度价值。

**第二轮结果（2026-09-24）**：0.8B / 2B / 4B × 23 个工具 × 31 题。JEV 调度只在 0.8B 上有明显收益
（42% → 55%），2B 持平、4B 反而下降，35B 原生 100%。原因：JEV 把工具选得更准，但「只填参数」的
小模型丢了意图，参数错误增加。另外两个可直接用的发现：JEV 决策领先幅度 < 0.3 时几乎必错
（14 条里 1 条通过），是「升级到云端」的可靠触发；验收问法改成「做对了或问对了」后误报从 19% 降到 10%。
**方向修正：从「JEV 选步骤、小模型填参数」改为「小模型提议、JEV 把关 + 没把握就升级」**，第三轮验证。
详见该目录 README。

**E2：多小的 JEV 还能用（2026-09-24，`docs/experiments/e2-jev-size/`）**：OpenJev 分别架在
Qwen3.5-0.8B / 2B / 4B / 9B(fp8) 与 35B 上。选工具的门槛陡峭地落在 **4B（96%，35B 为 99%）**，2B 只有 44%；
验收难得多，4B 的 AUC 0.72，35B 0.88；**「动手前预判本地能不能做」在任何尺寸上都接近掷硬币**。
由此得到分工：**本地 4B 一个模型兼任 JEV 与解码（选工具 + 填参数）；选择领先幅度低或单步检查不过 → 该步交给
云端解码；结束时由云端 JEV 验收（只做前向、成本低），不过 → 整题交给云端**。E3 验证单步检查与端到端路由。

**E3：16GB Mac 实测（2026-09-24，`docs/experiments/e3-quant/`）**：MLX 上一个进程同时当 JEV 与解码器。
**最小可用组合是 Qwen3.5-4B-4bit，峰值约 4 GB**：选下一步 91%、自己调工具 87%～94%；3bit 掉到 68% / 61%；
8bit 略准但生成速度减半；9B 选工具更差（76%）且每题 75 秒；35B-A3B 装不下。日常短任务 8K 上下文足够
（实测峰值约 3.3K token，工具定义占 2.6K）。M1 预填充只有约 178 tok/s，**工具定义前缀缓存是必须的**：
每题从 41 秒降到 10 秒。本地 4B 当验收员只拦得下 24% 的失败，验收交给云端 JEV 的结论不变。
