# E5：工具精简与渐进式披露

背景：[E4](../e4-e2e/README.md) 定下「本地 4B 做题 + 云端验收」。但 E1–E4 用的是 23 个精简工具，
真实 Agent 装配的是 34 个工具、定义 7.1K token（`dump-real-tools.ts` → `real-tools.json` 快照）。
这一轮回答：**真实工具集放到本地 4B 上会不会选乱？精简、分组、渐进式披露哪种最好？**

## 设置

- 本地：M1 16GB，Qwen3.5-4B-MLX-4bit（`../e3-quant/mlx_jev_server.py --prefix-cache --prefix-keep 8`），
  JEV 与解码同一进程；D 组另起 bge-small-en-v1.5（llama.cpp `--embedding`）。
- 工具：真实 34 个 + 路线图里的感知（转写 / OCR）与日程通讯（提醒 / 日历 / 联系人 / 邮件）6 个 = 40 个（`tools.ts`）。
- 任务：33 题（`tasks.ts`）——核心 10、单组 9、多步 7（含跨组 2）、不该调工具 4、该反问 3。
  打分：必需步骤按序出现且参数对；允许至多 2 次额外只读调用（真实工具改文件前要先读）；
  多余的副作用调用判错；反问题调 `ask_user` 或直接问都算对。

| 组 | 一开始给模型的工具 | 工具定义 token | M1 上不走缓存要读 |
|---|---|---|---|
| A 现状全量 | 40 个 | 7,694 | 约 43 秒 |
| B 精简扁平 | 核心 9 个（`recall` 合并知识库 / 笔记 / 记忆，`find` 合并 glob / grep / list_dir，去掉流程控制与 JEV）+ 全部组，22 个 | 4,025 | 约 23 秒 |
| C 核心 + JEV 选组 | 核心 + 同一个 4B 当 JEV 选中的组（第二名 p ≥ 0.25 也加载）+ `load_tools` 兜底 | 1,555～3,258 | 9～18 秒 |
| D 核心 + 向量选组 | 同 C，但用 bge-small 相似度选组 | 同上 | 同上 |
| E 核心 + 模型自己加载 | 核心 + `load_tools`（定义以工具结果形式追加在对话后面，不动前缀） | 1,555 起 | 约 9 秒起 |

## 结果（2026-09-25）

| 组 | 通过 | 核心 | 单组 | 多步 | 不该调 | 该反问 |
|---|---|---|---|---|---|---|
| A 全量 40 | **30/33（91%）** | 9/10 | 9/9 | 5/7 | 4/4 | 3/3 |
| B 精简扁平 22 | 29/33（88%） | 9/10 | 9/9 | 4/7 | 4/4 | 3/3 |
| **C JEV 选组** | **30/33（91%）** | 10/10 | 9/9 | 4/7 | 4/4 | 3/3 |
| D 向量选组 | 29/33（88%） | 10/10 | 8/9 | 4/7 | 4/4 | 3/3 |
| E 模型自己加载 | 26/33（79%） | 10/10 | 6/9 | 3/7 | 4/4 | 3/3 |

选组质量：

| 组 | 需要组的 14 题：开局就选全 | 不需要组的 19 题：开局多加载 | 模型调 `load_tools` | 其中补对 |
|---|---|---|---|---|
| C（JEV） | **14/14** | 6/19 | 0 | — |
| D（bge-small） | 8/14 | 17/19 | 4 | 3 |
| E（模型自己） | 0/14 | 0/19 | 11 | 8 |

耗时：这一轮各组耗时**不可比**。实验用的前缀快照是「与上一个请求的最长公共前缀」处拍的，公共前缀有时延伸进
用户消息，下一题对不上就重建，B 组因此几乎每题都重读 4K 前缀（单工具题也要约 20 秒）。
产品实现应在**结构边界**（工具定义块末尾）拍快照。可比的是上表的前缀长度。

### 结论

1. **4B 面对 40 个真实工具并没有选乱**：全量 91%，与精简 / 分组在 1～2 题的误差内。
   原先「工具多了小模型就选错」的担心在这组任务上不成立；**精简的收益主要是速度与内存，不是准确率**
   （前缀 7.7K → 1.6～3.3K，未命中缓存时首轮 43 秒 → 9～18 秒；前缀快照也小得多）。
2. **渐进式披露用「JEV 选组」**：开局就选全所需组 14/14，与全量一样准，前缀只有全量的 20～40%；
   多加载只发生在 6/19 题，代价是多几个工具而已。兜底的 `load_tools` 一次也没用上。
3. **不要让小模型自己找工具**（E，Anthropic Tool Search / 元工具那一类）：79%，最差。模型常常意识不到
   该加载（14 题开局都没有所需工具，只有 11 题去加载了），于是拿核心工具硬做（用 `recall` 找图、不查联系人就发信）。
   这类方法适合大模型，不适合 4B。
4. **英文向量模型选组不可靠**（D）：bge-small-en 对中文请求只选对 8/14，又在 17/19 题上多加载。
   若要走检索路线，需要中文 / 多语向量模型；JEV 选组顺带给出置信度，更合适。
5. **剩下的错误不是「工具给得多或少」的问题**：`m-minutes-email`（不查联系人就发邮件）在**五组全错**，
   `m-todo-speech`（不读文件就念待办）、`m-release-poster`（回复里漏了产物编号）也跨组出现。
   这些要靠参数层兜底（收件人必须来自联系人结果或用户原话，否则先查 / 先问）与云端验收，而不是工具披露。

### 对方案的修正

- 简洁模式：常驻核心工具 + **JEV 选组**（同一个本地 4B，一次前向）+ `load_tools` 兜底；按组合在工具块末尾拍前缀快照。
- 去掉流程控制类工具与 `jev_evaluate`：为了前缀长度，不是为了准确率；合并近义检索（`recall`）可以做，但收益未被这组题证明。
- 不做「模型自己搜索工具」的渐进式披露。
- 多步任务的遗漏交给参数层规则 + 云端验收（E4 的链路）。

## 复现

```bash
OMNI_DATA_DIR=$(mktemp -d) bun dump-real-tools.ts        # 可选：刷新真实工具快照
# 本地 4B（JEV + 解码）与 bge-small 向量服务
PYTHONPATH=<openjev>/src python ../e3-quant/mlx_jev_server.py --model <Qwen3.5-4B-MLX-4bit> --port 18130 --prefix-cache --prefix-keep 8 &
llama-server -m bge-small-en-v1.5-f16.gguf --embedding --port 18132 -ngl 99 &
bun bench.ts A,B,C,D,E        # 约 1.5 小时
bun analyze.ts results-e5.jsonl
```
