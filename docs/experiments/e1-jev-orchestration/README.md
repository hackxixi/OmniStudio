# E1：JEV 编排 + 小模型填参数

背景与设计见 [product-direction.md §7 / §9.1](../../product-direction.md)。

## 文件

| 文件 | 内容 |
|---|---|
| `tasks.ts` | 第一轮：8 个桩工具 + 26 个任务（L2 单步 18、L1 不该调工具 4、L3 两步 4）；桩结果里埋了只能从工具拿到的信息 |
| `tasks2.ts` | 第二轮：23 个工具（含近义工具）+ 31 个任务（近义工具 13、不该调 4、该反问 4、三到四步 10），另带 HINTS 用的两周日历与枚举说明 |
| `bench.ts` | 四组：A 小模型原生工具调用 / B JEV 选步骤 + 小模型约束解码填参数 / B0 同 B 但不按附件过滤工具 / C 中等模型原生工具调用 |
| `verify.ts` | 事后用 JEV `noul` 给所有组的每条运行判「处理对了没有」，与真值对照（`Q=v1` 是第一轮的问法） |
| `analyze.ts` | 第二轮结果按任务类别拆开，并把「选错工具」与「工具对、参数错」分开计数 |
| `run-r2.sh` | 第二轮驱动：0.8B / 2B / 4B 依次起、跑、停，最后 35B |
| `results-r1.jsonl` / `results-r2.jsonl` | 两轮原始结果（每行一条运行） |

在 ycs2 上跑（小模型容器 `~/jev/launch-e1-small.sh`，与 jev-sglang 共用 GPU4，**用完即停**——
它会吃掉 35B 的活动显存余量）：

```bash
cd /tmp/e1 && OUT=results.jsonl ~/.bun/bin/bun bench.ts A,B,B0,C       # 第一轮
nohup ./run-r2.sh > run-r2.log 2>&1 &                                 # 第二轮（约 30 分钟）
~/.bun/bin/bun analyze.ts results-r2.jsonl
SET=r2 ~/.bun/bin/bun verify.ts results-r2.jsonl
```

注意：launcher 的 `--mem-fraction-static` 按「可用显存 − 总显存 ×（1 − 比例）」折算，GPU4 已被 35B 占 ~40G，
0.8 时小模型实占约 20G，只给 35B 留 3～4G 余量；跑完务必 `docker stop e1-small`。

## 第一轮（2026-09-24）

环境：小模型 = 魔搭 `Qwen/Qwen3.5-4B`（bf16，SGLang 0.5.19，关思考）；中等模型 =
`Qwen3.6-35B-A3B-AWQ`（同版本 SGLang，关思考）；JEV = OpenJev on 35B（`:18110`）。temperature 0，单次运行。

| 组 | 通过 | 工具选对 | 参数正确 | 平均耗时 |
|---|---|---|---|---|
| A 4B 原生 | **92%** (24/26) | 100% | 92% | 1059 ms |
| B JEV + 4B | 88% (23/26) | 100% | 88% | 1531 ms |
| B0 JEV + 4B（不过滤） | 88% (23/26) | 100% | 88% | 1428 ms |
| C 35B 原生 | **92%** (24/26) | 92% | 92% | 793 ms |

### 结论

1. **这套任务对 4B 太简单，分不出高下。** 4B 原生工具调用已经 92%，JEV 编排没有带来准确率提升，
   反而多了约 45% 的耗时（每步多一次 JEV 调用 + 一次独立的最终回答调用）。
   **不能据此说 JEV 编排没用，只能说 L2 单步 + 8 个工具不是它该发力的地方。**
2. **JEV 选步骤本身很稳**：52 次决策全部选对（含 L1 该直接回答的 4 题），最低置信度 0.595；
   这组任务里「只给可行选项」没有体现出差别（B 与 B0 结果相同），只是让两次决策的领先幅度变小。
3. **剩下的错误全在参数里，而且是推理型的**：「下周一」算成 10-05（三组共 3 次）、
   「截止日前一天」没减一天、「竖版 / 横版」对应不到尺寸枚举。这类错误 JEV 选步骤兜不住，
   要靠工具侧：日期参数给日历上下文或接受相对时间、枚举值写清楚含义（`1024x1792 = 竖版`）。
4. **35B 原生也会犯「小模型式」错误**：给「改写一句话」调了语音合成；
   发票任务只做了 OCR 却回答「已为您设置提醒」—— **声称做了没做的事**。
5. **JEV 当验收员有用，且与编排方式无关**（`verify.ts`，104 条运行）：

   | 阈值 | 抓到的失败 | 误报 |
   |---|---|---|
   | 0.80 | 4 / 10 | 0 / 94 |
   | 0.85 | 5 / 10 | 0 / 94 |
   | 0.90 | 7 / 10 | 4 / 94 |

   抓得住：发票提醒日期错（0.50）、横版画成方图（0.73～0.76）、35B 谎称已设提醒（0.82）。
   抓不住：「下周一」算错日期（0.95～0.96，要做日历推理）、不必要的语音合成（0.87）。

### 对方向的影响

- 「JEV 当**验收员**」比「JEV 当**调度员**」先有收益：它可以套在任何编排方式外面，
  0.85 阈值下零误报地拦下一半错误，正好接「逐级升级到云端」。
- 「JEV 当调度员」要在更难的条件下再测：见下一轮。

## 第二轮（2026-09-24）

把任务推到小模型会崩的区域：魔搭 `Qwen3.5-0.8B` / `2B` / `4B`（bf16，关思考）× 23 个工具 × 31 题；
每个模型跑 A / B / B0，再带 HINTS（两周日历 + 枚举含义）跑 A / B；35B 原生跑 C。
（4B 的 4bit 量化这轮没做：SGLang 上没有现成的魔搭 4bit 版本，留到能力数据库的量化维度里测。）

| 组 | 总通过 | 近义工具 | 不该调 | 该反问 | 多步 | 选错工具 | 工具对、参数错 | 平均耗时 |
|---|---|---|---|---|---|---|---|---|
| 0.8B A | 42% | 8/13 | 3/4 | 1/4 | 1/10 | 11 | 6 | 653 ms |
| 0.8B B | **55%** | 9/13 | 4/4 | 3/4 | 1/10 | 5 | 7 | 1407 ms |
| 0.8B B+hints | **58%** | 9/13 | 4/4 | 3/4 | 2/10 | 4 | 7 | 1355 ms |
| 2B A | 65% | 12/13 | 1/4 | 1/4 | 6/10 | 9 | 1 | 791 ms |
| 2B B | 61% | 10/13 | 3/4 | 3/4 | 3/10 | 3 | 8 | 1119 ms |
| 2B A+hints | 65% | 11/13 | 0/4 | 2/4 | 7/10 | 8 | 1 | 746 ms |
| 2B B+hints | **71%** | 12/13 | 3/4 | 3/4 | 4/10 | 3 | 4 | 1061 ms |
| 4B A | 84% | 12/13 | 4/4 | 3/4 | 7/10 | 2 | 3 | 1567 ms |
| 4B B | 77% | 13/13 | 4/4 | 2/4 | 5/10 | 3 | 3 | 2079 ms |
| 4B A+hints | **87%** | 13/13 | 4/4 | 2/4 | 8/10 | 3 | 0 | 1591 ms |
| 4B B+hints | 84% | 13/13 | 4/4 | 2/4 | 7/10 | 3 | 1 | 2112 ms |
| 35B C | **100%** | 13/13 | 4/4 | 4/4 | 10/10 | 0 | 0 | 1118 ms |
| 35B C+hints | 97% | 13/13 | 4/4 | 3/4 | 10/10 | 1 | 0 | 1175 ms |

（B0 与 B 在三个模型上结果相同，表中省略；完整数据 `bun analyze.ts results-r2.jsonl`。）

### 结论

1. **JEV 调度的价值随模型变大而消失**：0.8B 上 +13 个点（42% → 55%），2B 上持平（带修正 +6），
   4B 上反而 −7，35B 原生已经 100%。**能跑 35B-A3B 的机器不需要 JEV 调度；它的用武之地是 ≤ 2B 的机器。**
2. **JEV 确实把「选哪个工具」选得更准**：选错工具 0.8B 11 → 5、2B 9 → 3；
   「不该调工具」和「该反问」两类进步最大（2B 的反问 1/4 → 3/4，不该调 1/4 → 3/4）。
3. **但拆开之后，填参数的小模型丢了意图**：2B 的「工具对、参数错」从 1 升到 8。典型错误：
   把工具名当参数填进去（`contacts_lookup(name="contacts_lookup")`，连填四次）、提醒日期错一天、
   「横版海报」填成方图。A 组里模型是按自己的计划填参数的，B 组的填参数模型只知道「下一步调 X」，
   不知道这一步是为了什么。**这是本方案当前形态的主要缺陷。**
4. **「只给可行选项」两轮都没体现出作用**（B0 = B），可以作为廉价保险保留，但不是关键。
5. **工具侧修正（日历 + 枚举含义）小而稳**：各组 +0～+10 个点，日期类错误明显减少。
   这是不依赖编排方式的改进，应该直接做进真实工具的描述里。
6. **JEV 的「没把握」信号非常准**：B 组运行中只要有一次决策的领先幅度 < 0.3，
   14 条里只有 1 条通过；其余 172 条通过 73%。**这是触发「升级到云端」的可靠依据。**
7. **验收员的问法要改**：第一轮的问法只问「完成了没有」，会把「信息不足时正确反问」判成失败
   （69 次误报里 41 次）。改成 v2 问法（「该做的做对了，或者该问的问了」）后：

   | 问法 | 阈值 0.8 抓到的失败 | 误报 |
   |---|---|---|
   | v1 | 119 / 161（74%） | 68 / 366（19%） |
   | v2 | 111 / 161（69%） | 36 / 366（10%） |

   第一轮数据上 v2 仍然零误报（4 / 10，0 / 94）。多步任务里的细节错误仍是漏判大户（17 次）。

### 对方向的影响

- 「JEV 选步骤、小模型只填参数」**这个拆法不对**：它修好了选工具，却把参数弄坏了。
- 更好的组合是 **「小模型提议，JEV 把关」**：小模型照常原生调用工具（保留意图和参数质量），
  JEV 只在三个地方插手——①对提议的下一步打分，强烈反对时才换成 JEV 的选择；
  ②领先幅度太低时**升级到云端**；③结束时用 v2 问法验收，不过关也升级。
- 这正好回答产品问题：**「本地小模型 + 云端兜底」能让多少比例的任务留在本地、最终准确率多少**。

## 第三轮计划

- **G**：小模型原生调用 + JEV 把关（强烈反对才改选，改选后才由小模型按新工具重填参数）；
- **G+升级**：G 之上，决策领先幅度 < 0.3 或 v2 验收 < 0.8 时，整题交给 35B（模拟云端）重做；
- 指标：最终通过率、**留在本地的比例**、云端调用次数（成本）、平均耗时；
- 模型：2B 与 4B（0.8B 基本不可用，作为下限参照跑一次即可），全部带 HINTS。
