# E2：多小的 JEV 还能用？

背景：[product-direction.md §7](../../product-direction.md)。E1 证明「JEV 的领先幅度」是可靠的升级信号，
但 E1 的 JEV 一直是 35B。这一轮回答：**把 OpenJev 架在多小的 Qwen 上，还能选对工具、判对完成？**
如果足够小，本地只需部署**一个**模型：同一个模型既当 JEV（判断）又当解码器（填参数 / 写回答），
共享权重和前缀缓存。

## 设置

- JEV 骨干：魔搭 `Qwen3.5-0.8B` / `2B` / `4B`（bf16）/ `9B`（**fp8**，GPU4 放不下 bf16）与现役
  `Qwen3.6-35B-A3B-AWQ`；OpenJev 同一镜像、同一份源码，小模型走 `~/jev/launch-e2-openjev.sh`
  （`:18120`，只听 127.0.0.1，`OPENJEV_IMAGES=off`）。注意 35B 是 3.6 代，其余是 3.5 代。
- 数据全部来自 E1 第二轮（`../e1-jev-orchestration/tasks2.ts` + `results-r2.jsonl`），三项考试：

| 考试 | 考什么 | 标准答案 |
|---|---|---|
| **select** 选下一步 | 68 个决策点，每点给 23 个工具 + finish（+ 首步的 ask_user），教师强制（历史都是正确的前几步） | 35B 原生第二轮全对的轨迹 |
| **verify** 验收 | 527 条运行，v2 问法「做对了，或者该问的问了」 | 第二轮打分 |
| **route** 自知之明 | 请求刚到时问「小模型能独立做对吗」 | 该尺寸小模型（A 组 + HINTS）的真实成败 |

```bash
# ycs2：/tmp/exp 下放 e1-jev-orchestration/{tasks.ts,tasks2.ts,results-r2.jsonl} 与本目录
cd /tmp/exp/e2-jev-size && nohup ./run-e2.sh > run-e2.log 2>&1 &     # 约 50 分钟，跑完两个容器自动停
```

## 结果（2026-09-24）

| JEV 骨干 | select | 其中：工具 | finish | 该反问 | verify AUC | 误报 ≤10% 时拦下的失败 |
|---|---|---|---|---|---|---|
| 0.8B | 35% | 16/37 | 8/27 | 0/4 | 0.51 | 2% |
| 2B | 44% | 3/37 | 27/27 | 0/4 | 0.53 | 12% |
| **4B** | **96%** | **37/37** | 26/27 | 2/4 | 0.72 | 21% |
| 9B（fp8） | 87% | 31/37 | 27/27 | 1/4 | 0.81 | 26% |
| 35B | 99% | 37/37 | 27/27 | 3/4 | **0.88** | **68%** |

route（预判小模型能否独立做对）的 AUC：

| JEV 骨干 | 预判 0.8B | 预判 2B | 预判 4B |
|---|---|---|---|
| 0.8B | 0.43 | 0.52 | 0.84 |
| 2B | 0.62 | 0.44 | 0.66 |
| 4B | 0.54 | 0.30 | 0.54 |
| 9B | 0.60 | 0.23 | 0.54 |
| 35B | 0.68 | 0.31 | 0.60 |

（4B 小模型只错了 4 题，「预判 4B」一列样本太少，0.84 这类数字不可信。）

### 结论

1. **选工具的门槛在 4B，而且是陡坡**：2B 几乎总选 finish（37 个该调工具的点只对 3 个），
   4B 直接到 96%，与 35B 的 99% 相当。**4B 是「一个模型兼任 JEV + 解码」的最小可行尺寸。**
   9B 反而低于 4B，可能是 fp8 量化或代际差异，未单独拆开。
2. **「该反问」是小 JEV 的共同短板**：4B 2/4、9B 1/4——信息不足时它们倾向直接选工具
   （把「给他发封邮件」判成 send_email）。这一类要靠参数层兜底（收件人为空 / 指代不明就反问），
   不能只靠 JEV。
3. **验收比选工具难得多，要大模型**：4B 的 AUC 只有 0.72，误报压到 10% 以内只能拦下 21% 的失败；
   35B 是 0.88 / 68%。验收是「看整段过程挑毛病」，比「从菜单里挑下一项」难一个量级。
4. **「预判自己做不做得到」在任何尺寸上都不成立**：AUC 基本在 0.5 上下，对 2B 甚至系统性反着判
   （0.23～0.31）。让 JEV 在动手前凭请求文本判断「本地能不能做」，等于掷硬币。

### 对你提出的方案的影响

你的设想是「同架构的一个模型既出 JEV 又解码，选工具时顺便判断能不能做，不能就交给云端填参数或整体执行」。
数据支持其中一半、否定另一半：

- ✅ **一个 4B 兼任 JEV + 解码是可行的**：选工具 96%。
- ❌ **「动手前预判能不能做」不可行**：要换成**观察到的信号**：
  1. **选择时的领先幅度**（E1：< 0.3 时 14 条里 1 条对）——这是选工具的同一次调用顺带给出的，零额外开销；
  2. **填完参数后的单步检查**：「这一步的工具和参数对不对」比整段验收窄得多，也许 4B 就够——**待测**；
  3. **最终验收交给云端 JEV**：JEV 不生成 token，只做一次前向，云端做验收的成本远低于云端解码；
     35B 在误报 ≤10% 时能拦下 68% 的失败。
- 推导出的分工：**本地 4B 负责选工具和填参数；领先幅度低或单步检查不过 → 这一步交给云端解码；
  结束时由云端 JEV 验收，不过 → 整题交给云端重做。**
