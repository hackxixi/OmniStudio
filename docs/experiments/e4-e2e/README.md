# E4：端到端「本地 4B + 云端兜底」

背景：[E3](../e3-quant/README.md) 定下 16GB Mac 的本地组合（Qwen3.5-4B-MLX-4bit，JEV + 解码同一进程，前缀缓存）。
这一轮把完整链路串起来跑：本地做题 → 各种信号 → 需要时交给云端，量出**最终准确率、留在本地的比例、云端花费、耗时**。

## 设置

- **本地**：M1 16GB，`../e3-quant/mlx_jev_server.py --prefix-cache`，Qwen3.5-4B-MLX-4bit。
- **云端**：ycs2 的 Qwen3.6-35B-A3B（SGLang）与 35B OpenJev，经 SSH 隧道访问（模拟 OmniLabs）。
- **任务**：E1 第二轮 31 题（23 个工具，HINTS=1）。
- **一次采集、离线推演**（`e2e.ts`）：每道题都记下
  1. 本地 4B 原生做题的结果；每一步动手前，同一个 4B 当 JEV 对「下一步」打分（选择、领先幅度、与模型实际提议是否一致）；
  2. 本地做完后，云端 35B JEV 用 v2 问法验收的 p；
  3. 云端 35B 从头做同一题的结果（temperature 0，确定性）。

  策略 = 在这些信号上设条件，升级则结果取云端、否则取本地（`policy.ts`）。

```bash
ssh -N -L 28110:127.0.0.1:18110 -L 28000:127.0.0.1:30000 ycs2 &
CLOUD_JEV_KEY=$(ssh ycs2 cat /home/yc/jev/openjev.key) bun e2e.ts     # 约 15 分钟
bun policy.ts results-e4.jsonl
```

## 结果（2026-09-24）

本地单独 29/31，云端单独 30/31。

| 策略 | 最终通过 | 留在本地 | 云端解码题数 | 云端解码 token | 云端 JEV 调用 | 平均耗时 | 升级里本地本来就对的 |
|---|---|---|---|---|---|---|---|
| 全本地 | 94% | 100% | 0 | 0 | 0 | 22.2 s | 0 |
| 全云端 | 97% | 0% | 31 | 208,216 | 0 | 1.4 s | 29 |
| 本地 JEV 领先幅度 < 0.3 | 97% | 71% | 9 | 75,570 | 0 | 22.6 s | 8 |
| 本地 JEV 与模型不一致 | 97% | 77% | 7 | 46,143 | 0 | 22.6 s | 5 |
| 不一致 或 幅度 < 0.3 | 97% | 58% | 13 | 100,459 | 0 | 22.9 s | 11 |
| 云端验收 < 0.8 | 97% | 90% | 3 | 17,993 | 31 | 22.6 s | 2 |
| **云端验收 < 0.9** | **100%** | **84%** | **5** | **40,295** | 31 | 22.8 s | 3 |
| 本地信号 或 云端验收 < 0.9 | 97% | 55% | 14 | 109,557 | 31 | 23.2 s | 12 |
| （上界）只在本地真错时升级 | 100% | 94% | 2 | 16,157 | 0 | 22.4 s | 0 |

耗时拆分：本地每题 22.2 s 里，**本地 JEV 把关占 12.1 s（54%）**，模型自己做题 10.1 s；云端验收每题 0.3 s、约 900 token。

### 结论

1. **「本地做 + 云端 JEV 验收 + 不过就云端重做」成立**：阈值 0.9 时 31 题全对（高于全云端的 97%），
   84% 的题留在本地，云端解码 token 比全云端少 81%，额外只多 31 次各约 900 token 的 JEV 前向。
2. **本地 JEV 逐步把关不值得，应该去掉**：
   - 它让本地耗时翻倍（每题多 12 秒）；
   - 作为升级信号，它升级的题大多本来就对（「不一致 或 幅度<0.3」升级 13 题，其中 11 题白花钱），
     叠加到云端验收上反而把准确率从 100% 拉回 97%、本地比例从 84% 降到 55%；
   - 主要误报来自「该反问」：模型正确地反问了，本地 JEV 却选了某个工具（E2 已发现小 JEV 的反问短板）。
   去掉之后本地每题约 10 秒。
3. **云端验收是性价比最高的一环**：它只看最终结果，只做一次前向，能区分「本地做错」与「本地做对了」；
   漏判的仍然有（`m-minutes-email` 验收 0.89，邮件正文不对），所以阈值宁高勿低。
4. **全云端最快（1.4 秒 / 题），本地慢一个数量级**：本地路线换来的是隐私、离线和成本，不是速度。
   产品上要把这件事说清楚，并允许「能力优先」档直接走云端。

### 修订后的推荐链路（16GB Mac）

1. 本地 Qwen3.5-4B-4bit 原生调用工具做题（前缀缓存，约 10 秒 / 题）；**不做本地逐步 JEV**；
2. 做完后把「请求 + 动作 + 回复」交给云端 JEV 验收（约 0.3 秒、900 token）；
3. p < 0.9 → 整题交给云端重做，并告诉用户原因和花费；
4. 失败 / 升级的题进失败案例库。

注意样本只有 31 题、且是本地模型本来就擅长的类型（本地单独 94%），阈值要在更难、更大的任务集上再校准。
