# E6：真实 App 里的回归（本地 4B，经典 vs 精简路由）

背景：精简路由工具策略（`AGENT_TOOL_STRATEGY=routed`，见 AGENTS.md）实现后，在**真实 App**里用本地候选模型
把 [E5](../e5-tool-disclosure/README.md) 的任务再跑一遍：真实 Agent、真实工具、真实系统提示。

## 设置

- **独立数据目录**（`seed.ts`）：不碰用户自己的 dev / canary / stable 数据。聊天走「远程」模式指向本机 llama-server
  （Qwen3.5-4B Q4_K_M，`--jinja` 解析工具调用，关思考，2 槽 × 16K）；JEV 走 cloud 后端指向
  `../e3-quant/llama_jev_server.py`（同一个 llama-server 的 JEV 接口，JEV 与聊天共用权重）。
  预置一条笔记、一条记忆、一张生图记录与工作区文件；知识库未预置（导入要配向量模型）；生图 / 语音 / 视频后端未配置。
- 数据目录路径要短：macOS 的 Unix socket 路径上限 104 字节，控制通道会以 `ENAMETOOLONG` 起不来
  （长路径时 `omi` 静默失效，只在日志里留一条）。本轮用 `~/.omni-e6` 软链接到临时目录。
- **任务**（`run.ts`）：E5 的 33 题去掉真实 App 里没有的感知 / 日程工具的 7 题，剩 26 题；每题一次 `omi agent run --json`。
  联网 / 生成 / 知识库题只核对工具与参数（结果取决于外部服务或未预置的数据）；笔记、记忆、文件、不该调工具题连回答一起核对；
  真实 App 会把相关记忆自动拼进用户消息，所以「我喜欢什么音乐」「笔记结论是什么」不调工具直接答对也算对。
  App 的 Agent 不是 temperature 0，单次运行有抖动。

```bash
OMNI_DATA_DIR=~/.omni-e6 WORKSPACE=<工作区> STRATEGY=routed bun seed.ts
OMNI_DATA_DIR=~/.omni-e6 bun run --cwd apps/studio start      # 用独立数据目录启动真实 App
OMNI_DATA_DIR=~/.omni-e6 WORKSPACE=<工作区> TAG=routed bun run.ts
```

- 本地 4B 的 Agent 不是 temperature 0，单次运行有抖动：`REPEAT=3` 让每题跑 3 次
  （结果行带 `rep` 字段 1..3，追加写同一个 jsonl），再用 `bun summarize.ts results-e6.jsonl`
  按 tag 汇总每题通过次数 / 总次数、整体通过率、耗时与调用次数，输出两张 markdown 表
  （旧行没有 rep 字段，按 1 次算；summarize 只统计，不重新打分）：

  ```bash
  OMNI_DATA_DIR=~/.omni-e6 WORKSPACE=<工作区> TAG=routed REPEAT=3 bun run.ts
  bun summarize.ts results-e6.jsonl
  ```

## 回归过程中修掉的两个产品 bug

1. **`omi agent run` 在模型预填充时被掐断**：Bun 连接 10 秒没有数据就断开，本地 4B 读 4～8K token 的提示要几十秒，
   CLI 报 `socket connection was closed unexpectedly`，而应用里的回合继续跑、占着推理槽，后续请求连环超时。
   `server.timeout(req, 0)` 对流式响应体无效；改为回合进行中每 5 秒写一行心跳（`b7f9700`）。
2. **本地小模型搜索打转与生成失败后反复重试**：见下方「循环守卫」（`f8b7f5c`）。

## 结果（2026-09-25）

| 组 | 通过 | 平均工具调用 | 单题最多 | 调用 ≥6 次的题 | 耗时中位（不计生图等待） | 三道生成题的调用次数 |
|---|---|---|---|---|---|---|
| 经典 | 14/26（54%） | 5.5 | 25 | 8 | 23 秒 | 10 / 4 / 19 |
| 精简路由 | 16/26（62%） | 4.3 | 40 | 5 | 33 秒 | 8 / 5 / 5 |
| 精简路由 + 循环守卫 | 16/26（62%） | 2.7 | 9 | 4 | 22 秒 | 1 / 1 / 8 |
| **精简路由 + 守卫 + 三条规则** | **21/26（81%）** | **2.3** | **7** | — | **19 秒**（平均 29 秒，无 600 秒等待） | 1 / 1 / 1 |

（「生图等待」：没配后端时生图工具会在 GUI 里弹配置窗口并等待，无头运行时要等满 600 秒，与策略无关；
第四行起已由「无人值守不弹窗」修掉。）

第四行的三条规则（`745f811`）：dev 组只给开发类请求、`ask_user` 没人应答后不许追问或转向 bash、
「记住…」类请求在本轮说明里要求先调 `remember`；另外生图在无人值守时不弹窗、直接失败并说明去哪配。
剩下 5 道里有 3 道是评分脚本与真实 App 的差异（真实图片引用是 `gen/xxx.png` 而非桩里的 `img_prev_7`；
真实网络搜到的 Bun 版本不是桩里的 1.4.7；经由记忆索引直接 `note_read` 而没先检索），
真正的模型问题是：横版海报没传尺寸、找文件前多查三次、知识库为空时如实说没找到（环境限制）。按行为算约 24/26。

### 多轮与云端验收（2026-09-25，`results-e6-v2.jsonl`，评分已对齐真实 App）

| 组 | 通过 | 通过率 | 平均耗时 | 中位耗时 | 平均工具调用 |
|---|---|---|---|---|---|
| 经典（2 轮） | 32/52 | 62% | 73.9 秒 | 28.0 秒 | 5.7 |
| 精简路由（3 轮） | 64/78 | 82% | 29.5 秒 | 16.7 秒 | 3.0 |
| **精简路由 + 云端验收（escalate，1 轮）** | 23/26 | **88%** | 28.2 秒 | 21.1 秒 | 2.2 |

云端验收这一组：选组用本地 4B JEV，验收用 ycs2 上的 35B JEV（SSH 隧道），不通过交给 35B 聊天模型接着做。
25 次验收里 **14 次判不通过（56%）**，远高于 E4 桩环境的 16%：

| 类别 | 例子（判定值） | 性质 |
|---|---|---|
| 真做不到 | 网页不存在 0.25、知识库为空 0.75 / 0.44 | 判得对，但升级到云端也做不出来 |
| 该反问的题 | 给他发邮件 0.18、帮我画张图 0.27、设个提醒 0.80 | **误报**：无头运行里 `ask_user` 返回「不可用」，JEV 把这条失败的工具结果当成没做对 |
| 创作类 | 四行短诗 0.47、翻译 0.68 | **误报**：35B JEV 对开放式输出偏严 |

结论：云端验收确实把通过率再抬了 6 个点（82% → 88%），但阈值 0.9 在真实 App 里太严，**升级比例 56% 意味着一半以上的回合要多花一次云端解码**。
阈值降到 0.7 时升级降到 7/25（28%），砍掉的主要是 0.73～0.89 的边界判定。后续：
- 默认阈值改 0.7，或按任务类型分阈值（创作 / 闲聊放宽）；
- 验收状态里把「`ask_user` 无人应答」标成「已向用户提问、等待回答」，而不是一条失败的工具结果；
- 「真做不到」的情况（数据不存在）升级无益：验收判不通过且本轮工具结果全是「没找到」时，不升级、只如实告知。

### 校准后重跑（v3，`results-e6-v3.jsonl`，阈值 0.7，1 轮）与升级失效的发现

校准（`857985a`：默认阈值 0.7、无人应答的提问写成「已问待答」、查找全空不升级）之后，同一套环境重跑云端验收组：

- **升级比例 56% → 31%**（8/26）。「给他发邮件」判定 0.18 → 0.65、「帮我画张图」0.27 → 0.38，仍低于 0.7；
  「查找全空不升级」本轮没触发（知识库题验收直接判过 0.95，另一题读了文件，不算「只查找」）。
- 通过 18/26（69%），8 道失败全是本地模型在验收**之前**的动作：联网题反复搜（Bing 结果杂、bun.sh 403）、
  翻译题去调工具、「帮我画张图」问不到人就直接生图、以及工作区残留（每题只重置 3 个预置文件，
  前几轮写出的 `notes/travel.md`——一份模型编的住宿标准——还在，被「查知识库再写文件」那题读到）。

**更重要的发现：升级这一步从来没有生效过。** 升级回复里是云端模型的整段思考、`</think>` 和未解析的
`<tool_call><function=recall>…` 原文，直接成了给用户的正文。原因是 ycs2 上的 SGLang（`jev-sglang`，:30000）
启动时没带 `--tool-call-parser` / `--reasoning-parser`：带工具请求 `/v1/chat/completions` 时返回
`tool_calls: None`，思考混在 content 里。所以 v2 里「+ 云端验收 88%」的升级部分并不成立——云端模型一个工具也没调成，
评分只看工具调用，没看出来。验收判定本身走 openjev（:18110）原生接口，不受影响。

据此的修正：
- 升级回复里出现 `<think>` / `</think>` / `<tool_call>` / `<function=…>` 原文时整段作废、保留本地结果，
  记 `agent.escalate.malformed`（`escalationLeakedMarkup`）——什么厂商都不该把这些显示给用户；
- 循环守卫：`ask_user` 没人应答后，本轮也不许调生成类工具（问的就是「画什么」）；
- `run.ts` 每题开始前清空整个工作区再写预置文件；
- 服务端：`jev-sglang` 启动脚本加 `--tool-call-parser qwen3_coder --reasoning-parser qwen3`，之后重跑升级组。

### 结论

1. **经典策略在 8K 上下文里跑不起来**：真实 Agent 的经典请求约 8.7K token，被 8K 槽直接拒绝；精简路由开局约 3K。
   16GB 机器上本地 4B 要么用精简路由，要么给到 16K 以上的上下文。
2. **精简路由比经典好**：54% → 62%，而且 JEV 选组在真实 App 里同样准（文件 / 记忆题判为只用核心工具，创作题加载 creation；
   边界题如「念待办」概率接近时，模型自己用 `load_tools` 补齐）。
3. **循环守卫把打转压下来了**：平均调用 4.3 → 2.7，单题最多 40 → 9；语音 / 视频失败后不再重试（8、5 次 → 1、1 次），
   知识库为空时的搜索从 80～200 秒降到 35～38 秒。
4. **通过数没涨，因为暴露了下一类问题**：
   - **无头运行里 `ask_user` 没人答**，模型追问几次后 `load_tools` 加载 dev 组、用 `bash` 硬做（`ask-email`、`l1-translate`）。
     在真实界面里用户会回答，这类失败有一部分是无头运行的产物；但「问不到就改用 bash」本身是该拦的行为。
   - **`remember` 没被调用**：说「记住我对花生过敏」时模型只口头答应（两个策略都这样）。
   - **多步任务仍会漏步骤**（先检索再写文件、导出素材），与 E5 结论一致，要靠云端验收兜底。
